<objective>
Wire emit() calls into the Pipeline state machine so a real or mock EventBus
receives the full event lifecycle (RUN_STARTED, RUN_COMPLETED, EPISODE_STAGE_CHANGED
with started+completed status per stage, DOWNLOAD_PROGRESS, ENCODE_PROGRESS,
EPISODE_COMPLETED, EPISODE_FAILED) for every pipeline run. Add per-feed counter
fields (episodes_done, episodes_failed, episodes_total) to the _Stores dataclass
so EPISODE_COMPLETED / EPISODE_FAILED payloads can embed feed_done / feed_failed /
feed_total. End-to-end vertical slice: tests prove that with event_bus injected,
the run loop produces the documented event sequence with the documented payload
shapes; with event_bus=None, no emits occur and the pipeline behaves exactly as
before.
</objective>

<threat_model>
ASVS L1 considerations for pipeline event instrumentation:

- Information disclosure via event payloads: payloads include guid, feed_slug,
  outcome, error text, and percent — all already logged today. No new sensitive
  fields (no credentials, no full file paths, no API keys). Error strings come
  from the existing exception chain; the payload uses a short error message
  (str(exc) at the failed-episode site) — same content already written to logs.
- Denial of service via unbounded queue growth: emit() uses put_nowait() on an
  unbounded asyncio.Queue. A stalled subscriber can grow the queue without
  bound. Accepted for Phase 2 (single-user local tool, deferred per CONTEXT/
  RESEARCH §8). Not addressed in this plan.
- Tampering: emit() is in-process only — no external trust boundary crossed.
- Auditing: every emit is paired with the existing logger output; no
  observability is removed.
</threat_model>
